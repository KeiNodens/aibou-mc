# mod 知識の取得と知識化 (D40, 2026-11-01)

aibou-mc がモッド環境を「知っている」状態を作るための設計。
知識は4層から取り、読み手は2系統 (コード / LLM) に分ける。
横断ルール:

- 知識ファイルにはパックの指紋 (モッド一覧のハッシュ) を刻み、
  パック変更時に古い知識だと検出できるようにする。
- LLM 向けの読み先は knowledge ツール1本に寄せる。
- コード向けは data ファイルと定義ファイル (machines/ 等)。

## 層1: ゲーム内データ (機械取得)
レジストリ / レシピ / タグ / モッド一覧は取得済み
(registry.blocks、recipe.lookup、meta.mods)。
残り: energy の実測 (Forge Energy capability を読む op) と
アイテム全体の索引 (data/item-index.json、再生成可能な事実
ファイルとして置き、手で編集しない)。
限界: 正確だが意味が無い (チャンネル数のような規則は無い)。

## 層2: jar 同梱ドキュメント
Patchouli のガイド本 JSON、lang ファイル、mods.toml を
抽出スクリプト (tools/) で knowledge/<modid>/ に原文保存し、
検索索引を1個作る。knowledge ツールの材料であり、定義を
書くときの一次資料でもある。
限界: ガイドが無い mod も多い。GUI の具体形までは無い。

## 層3: ソース解析 (wiki ではなくソースから wiki 化する)
wiki はデータが薄いことが多いので一次資料にしない。
mod のソース (パック収録バージョンに対応するタグ) を読み、
LLM の解析パスで規則と定数を抽出してルールファイルに
蒸留する。トークン予算は制約にしない (プレイヤーの方針)。
- コードが読む規則: JSON (例: ケーブル種別 → チャンネル数。
  schematic の cable_run 検証が読む)
- LLM が読む規則: md (knowledge ツール経由)
- 各ルールには出典 (repo@commit + ファイルパス) を必須とし、
  コードが消費する数値は値レベルの原文引用を付ける。
限界: 1テーマずつ。当たった所から貯める。

### 層3の整備 (D42、解析そのものより先に用意した土台)
- 解析結果は mod-knowledge/ (リポジトリにコミットする共有
  ストア) に置く。層2の抽出 (knowledge/、パックごと・生成物)
  とは置き場所を分ける。
- キャッシュキーは mod id + バージョン + ソース commit。
  **同じ mod の同じ版は、インスタンスやパックが何個あっても
  1回だけ解析する** (プレイヤーの指摘)。版が違えば別エントリ。
- tools/fetch_mod_source.py: sources.json の登録から repo を
  解決し、版に対応するタグを shallow clone して
  mod-knowledge/.sources/ にキャッシュ (既存なら再取得しない)。
- tools/knowledge_coverage.py: パックの層2索引とルール
  ストアを突き合わせ、解析済み/未解析の一覧を出す。
- knowledge ツールはルールも検索対象に含む (kind=rule)。

## 層4: 実機観測 → 実機検証フェーズに統合
独立したパイプラインは作らない。実機検証のバッチ (検証
チェックリスト) の中で画面・container のスナップショットを
data/probes/ に貯め、オフラインで定義と commission plan に
起こして machines/*.json の verified を上げる。層4の成果物は
層1的に消費できる形 (定義ファイル) になる。

## 応答層: プレイヤーへの回答と実演 (プレイヤーの追加)
プレイヤーがチャットで分からない事を聞いたら、LLM 側が
層1〜4を基に答える。knowledge ツール + その場の実測
(層1) を引いて文章で答えるのが基本形。
文章より実物が早い場合は、実際に機械を配置して見せる
(ミニ実演: schematic プリミティブで小さな実例を組み、
必要なら commission まで通して動かしながら説明する)。
実演の置き場所はプレイヤーの近く、小さい footprint で。
