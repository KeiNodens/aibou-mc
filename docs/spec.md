# Minecraft Together 要件仕様書

- バージョン: 0.2 (review-2026-10-27.md 指摘反映)
- 作成日: 2026-10-27
- 対象読者: 実装者 (Devin/プレイヤー) および LLMエージェント (ホストLLM)

## 1. 目的

mod環境のMinecraft Java版 1.20.1 (Forge 47.4.28) のワールドを、LLM駆動エージェントと人間が一緒に遊ぶためのシステムを構築する。エージェントは実プレイヤーとしてワールドに参加し、ゲーム内チャットで会話し、依頼された作業をこなし、状況を報告する「相棒」として振る舞う。

## 2. 背景

`research/` の調査に基づく。

- 既存のMCP実装 (yuniko版・lafkpages版) は Forge 1.20.1 では動作しない。前者はMineflayer経由で1.21.x向け、後者はFabric 1.21.8+Baritone依存。
- MineflayerをフォークしてFML3ハンドシェイク・動的レジストリ・mod固有ペイロードに対応する案 (research/Mineflayer_Forge対応フォーク設計.md) は実現可能だが、L2(動的レジストリ)を山とする実装リスクを抱える。
- そこで本線は「本物のForgeクライアントをアバター化する」方式 (案3) とし、実績の薄いBaritone Forge版に阻まれた場合は「サーバー側フェイクプレイヤー」方式 (案1) へ退く二本立てとする。

## 3. 用語

| 用語 | 意味 |
|---|---|
| System2 | LLM側の思考・計画層。Muse「ホストLLM」などMCPクライアントが担う |
| System1 | 高速実行層。移動・採掘・戦闘反射など即応性が要る処理 |
| agent-mod | 第2Minecraftクライアントに導入する自作Forge mod。WebSocket APIを公開する |
| bridge | MCPサーバー。agent-modとMCPクライアント (ホストLLM) の間を繋ぐNode/TypeScriptプロセス |
| 技能 (skill) | bridge側に置く複合動作の単位。gather・craft・follow 等 |
| パック | mod群の構成。dev=軽量検証用、prod=本番262mod |
| 実行管理状態 | 長時間操作の受理・進行・結果を識別するtask_id付きの状態。mod側で一時保持し、bridgeから照会する。観測データとは別に管理する |

## 4. スコープ

### 4.1 対象 (MVP・相棒型)

プレイヤーがチャットで指示を出し、エージェントが会話しながら実行・報告する形態。追従・移動・採集・クラフト・受け渡し・護衛・状況報告を主要機能とする。

### 4.2 拡張 (後続フェーズ)

自律モード。放置時にVoyager式の自動カリキュラムで探検・発展し、検証済みコードをスキルライブラリに蓄積する。設計書に拡張章を用意するが、MVPの受入条件には含めない。

### 4.3 非対象

公開サーバーでの利用、Bedrock Edition、音声入出力、画像認識ベースの操作、PvP最適化、大規模建築 (Baritone Builderはalpha級のため)。mod加工設備の自動操作はFR-05の段階対応として扱い、MVPでは標準作業台まで。設備ごとの個別最適化や設定GUIの深部連携は対象外。

## 5. 機能要件

| ID | 要件 | 優先度 |
|---|---|---|
| FR-01 | エージェントは実プレイヤーとして専用Forgeサーバーに接続・ログイン・スポーンできる | 必須 |
| FR-02 | ゲーム内チャットを双方向に読み書きできる (MCPツール: send_chat / get_chat)。さらに発話をトリガにホストの推論を開始できる契約 (イベント待機ツールとイベントバッファ) を提供する | 必須 |
| FR-03 | 座標指定移動・プレイヤー追従・経路探索・停止/キャンセルができる (Baritone) | 必須 |
| FR-04 | ブロック種別・個数を指定した探索採集ができる | 必須 |
| FR-05 | バニラ及びmodレシピのクラフトができる。範囲は標準作業台レシピに限らず独自RecipeType (機械・液体・エネルギーを使う加工) まで含む。対応は段階的で、標準作業台レシピ→列挙したmod加工設備の順 (対象列挙は design.md §6.5) | 必須 |
| FR-06 | 指定アイテムをプレイヤーへ手渡し・チェストへ格納できる | 必須 |
| FR-07 | 指定entityの攻撃・範囲護衛ができる | 高 |
| FR-08 | ブロック設置・ブロック/entityへの使用ができる | 必須 |
| FR-09 | 位置・体力・空腹・インベントリ・近傍ブロック/entity・バイオーム・時刻・イベント差分を観測データとして返せる。インベントリは全量集計の要約形式と、slot・属性・世代識別を含む詳細形式の2種を返せる | 必須 |
| FR-10 | modアイテム/ブロックをレジストリ名 (modid:name) で識別・操作できる | 必須 |
| FR-11 | タイムアウト・停滞・明示エラーを構造化メッセージで返し、LLMの再計画を助ける。長時間操作は受理時にtask_idを返し、状態照会・結果取得・停止完了の確認ができる | 必須 |
| FR-12 | bridgeのskills/ディレクトリにJSモジュールを置くだけで技能を追加・ホットリロードできる | 高 |
| FR-13 | Prism Launcher CLI経由でbotインスタンスを起動でき、切断時は自動再接続する | 高 |
| FR-14 | 危険操作 (大規模掘削・TNT・溶岩等) に確認フックを設けられる (config制御) | 中 |
| FR-15 | MCP経由で bot_status / cancel_current を呼べる | 中 |
| FR-16 | ゲーム内発話→ホスト推論→ゲーム内返信の起動経路が成立する。MVP検証ホストはCodex (bridgeのrunner経由で起動)。Muse連携は後続 (接続手順案は docs/muse-connection.md に準備済み、未接続) | 必須 |

## 6. 非機能要件

| ID | 要件 |
|---|---|
| NFR-01 | 同一PC上で「ユーザーのクライアント・専用サーバー・botクライアント」の3プロセスが同時稼働すること。RAM配分目安は 10GB + 8GB + 8GB。他アプリは終了前提 (ユーザー確認済) |
| NFR-02 | 原始操作ツールの応答はローカルで500ms程度を目安とする。長時間技能は非同期実行とし、進捗・完了をイベントで通知する |
| NFR-03 | bridgeはWS切断の自動復旧・botクライアントの再接続を行う。観測状態は都度取得しツール呼出間で記憶しない (mc-mcp方式)。一方、実行管理状態 (task_id・進行状態・結果) はmod側で一定期間保持し、再接続後も照会できる。実行世代のIDにより旧タスクと判別する |
| NFR-04 | Forge 47.4.28 / Minecraft 1.20.1 と 262個のmod群と同居できること |
| NFR-05 | 技能層はJSのホットリロードで開発できること。イテレーションはdevパックで高速化する |
| NFR-06 | MITライセンスで公開可能な構成とし、英語READMEを用意する。LLMはMCP標準経由で特定モデルに依存しない。APIキー・ワールドデータをリポジトリに含めない |
| NFR-07 | 対象環境は Windows 11。開発及びサーバー/botインスタンスは JDK 17 系、bridgeは Node LTS。既存のプレイ用インスタンスには触れない (別インスタンスとして構築) |

## 7. 制約

- Baritone Forge版 (v1.10.3) は262mod環境での実績が薄く、Mixin衝突リスクが本線方式の最大の不確実性。設計書の判定ゲートG1/G2で評価する。
- 262modパックにはクライアント専用modが含まれ、専用サーバー構築時に仕分けが必要 (mods.tomlのside情報等で機械分類)。
- BaritoneはMavenリポジトリを持たないため、jarをローカル依存として扱う。
- botの表示名はMinecraft IDの英数字制約上 `Rin` 等に限定される。configで変更可。

## 8. 成功基準 (MVP受入)

- チャットで「原木を集めて」と依頼すると、エージェントが理解・採集・帰還・受け渡しまで一連を完了する。
- 「ついてきて」で追従を開始し、探索後に迷子にならず帰還できる。
- 周囲スキャンでmodブロック名 (modid:name) が正しく取得できる。
- ゲーム内チャットへの一言から、MVPホスト (Codex) 上で返答と操作が始まる。
- 30分の連続プレイでbotが異常終了・応答不能にならない。

## 9. フォールバック条件

設計書の判定ゲートで以下が確認された場合、本線 (案3) を捨てて退路へ移行する。

- G1: devパックでBaritone Forge版が起動・経路探索できない、または代表modと衝突する。
- G2: prodパックでbotクライアントが実用レベルで起動しない・不安定である。

退路の第一候補は案1 (サーバー側フェイクプレイヤーmod) だが、その実現性は現時点で仮説である。移行に入る前に、移動・採掘・コンテナ操作の最小実証を行う。成立が見えなければ案2 (Mineflayerフォーク) の再評価も視野に入れる。bridge側の技能・MCP面・プロトコル仕様が流用できるよう、modとのプロトコルは画面座標ではなく意味操作 (コンテナのslot操作等) で定義し、各実装が対応機能一覧と未対応エラーを返す契約とする。
