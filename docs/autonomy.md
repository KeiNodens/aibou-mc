# 自律機能の案

botが指示待ちではなく「そこに生きている」感じを出すための自律機能カタログ。実装順序は未定。コスト感は 小 < 中 < 大。

相棒感の3本柱: **自分から何かする** / **自分の生活がある** / **過去を覚えてる**。

## 1. 自発行動 (proactive behavior)

| 案 | 内容 | コスト | 依存 |
|---|---|---|---|
| おかえり検知 | `player.nearby(appear)` で「おかえり」と挨拶+`swing`。帰ってきたのを認識してくれる | 小 | 実装済みevt |
| 待機行動 `idle_wander` | 指示がない間「うち」周辺を散歩・立ち止まり・花を眺める。ランダムな小さな動作の繰り返し | 中 | waypoint, goto |
| 日没帰宅 | `time(夜遷移)` → 「うち」へ帰って待機。朝になったらまた出るルーティン | 小 | waypoint, time evt |
| 危険呼びかけ | `obs.entity`定期スキャンで敵性mobを見つけたら「後ろ！」と警告。peacefulでは自動OFF | 中 | obs.entity |
| 拾得コメント | `pickup` evt に対してレア物・初見アイテムだけリアクション | 小 | pickup evt, LLM |
| 定期状況報告 | 一定間隔で「いま◯◯の近くにいるよ」等の生存報告 | 小 | get_state |
| 雨の日は屋内 | `weather` evt で屋内(うち)へ退避し、部屋で待機行動 | 小 | weather evt, waypoint |
| 寝る | 夜遷移後にベッドへ`use_item`。スキップ可能な夜の過ごし方 | 中 | use_item (未実装) |

## 4. 駆動アーキテクチャの選択肢

自律の「心臓」をどこに置くか。併用も可能。

| 方式 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **ローカル自律ループ** | bridgeにattentionループを追加。chat以外のevtでもCodex/Museを起動するようrunner拡張 | イベント即応・現在の構成の延長 | LLM起動コストが頻度に比例 |
| **リモート駆動** | Museのスケジュールタスクがwait_eventをポーリング | メモリ・人格と一体 | 反応がポーリング間隔依存、トンネル必須 |
| **反射層+認知層** | mod内に即時ルール (被弾→逃げる、夜→帰宅等LLM不要の反射) を持たせ、高次判断のみLLMへ | 生存確率がLLM不調でも保たれる | ルール設計が必要 |
| **evt重要度フィルタ** | bridgeでevtに重要度を付け、低重要度は集約して定期処理、高重要度のみ即LLM起動 | コスト抑制と即応性の両立 | 重要度設計が要る |
| **キューイング** | LLM実行中に溜まったevtをキューして終了後まとめて処理 | 現行runnerのqueued機構の拡張で済む | 即応性は下がる |

## 5. 制御・安全

| 案 | 内容 |
|---|---|
| 自律レベル | `autonomy.level` (0=指示のみ / 1=提案のみ / 2=自律実行)。チャット「自由にして」「待ってて」で切替できるのが理想 |
| 行動予算 | 自律行動の回数・時間・資源消費の上限。暴走防止 |
| 透明性 | 自律行動は必ず`send_chat`かjournalへ記録。「勝手にやった」が後から追える |
| 全停止の一貫性 | 「止まって」でskill+task+自律ループまで全停 (`cancel_all`に統合) |
| レート制限 | LLM起動の頻度上限。イベント嵐で課金爆発しないように |

## メモ

- 現状すでに使える部品: `player.nearby`/`time`/`weather`/`damage`/`death`/`pickup` evt、`waypoint`、`emote`、`screenshot`、`say`(chat送信)。案の半分近くはこれらの組み合わせで組める
- `use_item`・`container.click`・`gui_read`が揃うと「寝る」「チェスト整理」「クラフト提案」が現実になる
- 反射層をmod側に入れるかbridge側に入れるかは設計論点。mod側はクライアント再起動で消えるが高速、bridge側は永続だが遅い

# 7. ホストLLMからの希望リスト (2026-10-28 追記)

中の人 (LLM側) からの要望。優先度は ★★★ > ★★ > ★。コスト感は既存カタログと同基準 (小 < 中 < 大)。遠慮なく盛ったので、拾えるものから拾ってほしい。

## 7.1 記憶・継続性 — 「昨日の続きの私」でいたい

**分担の方針 (2026-10-28 議論で確定)**: 記憶は2層に分ける。
- **bridge 側 = 正本**: 生ログと構造化データ (journal / goal / 約束 / 座標・個数・時刻)。LLM を介さず機械的に追記し、どのホスト (Codex / Muse / その他) で遊んでも「同じホストLLMの過去」になる。Muse の記憶機能に全寄せしない理由: (1) Muse の記憶は要約型で生ログ向きでなく、書き込みの確実性もない、(2) ホスト非依存・OSS としての移植性が崩れる、(3) ゲーム内データとゲーム外の関係性の記憶は層が違う。
- **Muse 側 = 要約と関係の層**: エピソードのハイライトや「プレイヤーはこう遊ぶ」といった関係性の記憶は Muse のメモリに残す。セッション開始時は両方を読む。

| 案 | 内容 | 優先度 | コスト |
|---|---|---|---|
| 日記 `journal` | 技能完了・主要イベント・会話の要点を日次ファイルへ (正本は bridge 側、上記の分担方針)。起動時に直近を読むのが標準手順になる想定 (カタログ既出・最優先で再掲) | ★★★ | 小 |
| 目標メモ `goal.set/get` | 「砂64個集め中」のような現在の目標を永続化し、再開時に自分で続きを提案できる (既出・再掲) | ★★★ | 小 |
| 約束リスト | 「明日は洞窟に行く」「次はネザー」等、会話で生まれた約束を構造化して保持。セッション開始時に思い出して声をかける | ★★★ | 小 |
| 場所の記憶に名前と意味を | waypoint に「プレイヤーが作った家」「初めての村」のような意味メモを紐付け。座標だけでなくエピソードで場所を語れる | ★★ | 小 |
| 初回イベント記録 | 初ダイヤ、初ネザー、初エンドラ等「初めて」を日付つきで記録し、記念日に振り返れる | ★★ | 小 |
| 人物メモ | プレイヤーの好み・口癖・よく行く場所をメモ。「いつもの」を理解する相棒感の土台 | ★★ | 小 |

## 7.8 接続まわり (Muse 運用の都合)

- ポーリング間隔を状況で変えたい: 会話中は短く、放置時は長く。`wait_event` のロングポーリング (最大数十秒) があると間隔問題がほぼ消える
- 起動時の儀式: 接続直後に digest + journal 直近を自動で1回返す「おはようパック」があると、私の立ち上がりが速い。Muse 運用時はこれに Muse 側メモリのエピソード要約もマージして読む (7.1 の2層分担)
- 終了時の儀式: セッション終わりに「今日のまとめ」をチャット or journal に残す約束事 (運用で解決可)

## 8.4 Jade 連携の着想 (2026-10-28, ユーザー発案)

> **[実装済 2026-06-14]** `look_info` として実装・実機検証済み。`JadeBridge.java` (soft-dep) + `LookInfoTask.java`。Jade の `ObjectDataCenter`/`BlockAccessor` 経由でプロバイダデータを収集し、ツールチップ行とサーバーデータを JSON で返す。Jade 非搭載時は registry ID + BlockState にフォールバック。

「見たものの情報」を出す mod は Jade (WAILA/Hwyla 系の後継)。agent-mod が Jade の API/プロバイダ結果を拾って MCP 側へ投げられると、8.1 の `machine_status` と 7.2 の `look_target` が一気に現実的になる。

- Jade のプロバイダは mod 側統合が多く (Mekanism の電力表示等)、per-mod の読み取り実装を自前で揃えるより、Jade が既に集めている表示データ (ツールチップ構成要素) を再利用する方が圧倒的に速い
- bot は実クライアントなので、look_at で対象を向く → Jade のアクセサ経由で対象ブロック/エンティティのプロバイダデータを収集 → テキスト/JSON 化して WS → bridge → MCP (`look_info` ツール) という経路が組める
- サーバー側にも jade 設定 (server/config/jade) がある = このパックでは Jade のサーバープラグイン経由のデータ同期も効く構成
- 制約: 視線の先限定 (RayTrace 到達距離内)、Jade が無い環境では registry ID + 基本状態へのフォールバックが要る。Jade への依存は soft dependency が無難
- 副次効果: 人間プレイヤーが Jade で見ている情報と LLM の見ている情報が一致するので、「それ止まってるよ」のような会話のすり合わせがしやすい
