# 自律機能の案

botが指示待ちではなく「そこに生きている」感じを出すための自律機能カタログ。実装順序は未定。コスト感は 小 < 中 < 大。

相棒感の3本柱: **自分から何かする** / **自分の生活がある** / **過去を覚えてる**。

## 1. 自発行動 (proactive behavior)

| 案 | 内容 | コスト | 依存 |
|---|---|---|---|
| おかえり検知 | `player.nearby(appear)` で「おかえり」と挨拶+`swing`。帰ってきたのを認識してくれる | 小 | 実装済みevt |
| 待機行動 `idle_wander` | 指示がない間「うち」周辺を散歩・立ち止まり・花を眺める。ランダムな小さな動作の繰り返し | 中 | waypoint, goto |
| 日没帰宅 | `time(夜遷移)` → 「うち」へ帰って待機。朝になったらまた出るルーティン | 小 | waypoint, time evt |
| 危険呼びかけ | `obs.entity`定期スキャンで敵性mobを見つけたら「後ろ！」と警告。peacefulでは自動OFF | 中 | obs.entity |
| 拾得コメント | `pickup` evt に対してレア物・初見アイテムだけリアクション | 小 | pickup evt, LLM |
| 定期状況報告 | 一定間隔で「いま◯◯の近くにいるよ」等の生存報告 | 小 | get_state |
| 雨の日は屋内 | `weather` evt で屋内(うち)へ退避し、部屋で待機行動 | 小 | weather evt, waypoint |
| 寝る | 夜遷移後にベッドへ`use_item`。スキップ可能な夜の過ごし方 | 中 | use_item (未実装) |

## 2. 記憶・生活サイクル

| 案 | 内容 | コスト | 依存 |
|---|---|---|---|
| 日記 `journal` | 技能完了・主要イベントをbridgeが日次ファイルに記録。`read_journal`ツールで「昨日洞窟で迷った」の会話が成立 | 小 | bridge側のみ |
| 目標メモ `goal.set/get` | 永続化された「今の目標」。セッション断絶後も「砂64個集め中」を引き継ぎ、起動時に続きを提案 | 小 | waypoint方式の流用 |
| 計画メモ | 日記とは別に「次やることリスト」。目標達成したら自分で次を書き換える | 小 | bridge側のみ |
| 自発タスク提案 | インベントリや状況から「木が少ないから集めてくる？」と提案。許可制/自動実行の2モード | 中 | get_state + LLM |
| かくれんぼ | 「探して」→ 半径64内の隠れ場所へ移動、距離ヒント(暑い/寒い)を返す遊び技能 | 中 | goto, obs.entity |
| 宝探し | ホストLLMがアイテムをチェストに隠してヒントを出す、または逆 | 中 | container操作 |

## 3. 環境認識の能動化

| 案 | 内容 | コスト | 依存 |
|---|---|---|---|
| 構造物発見報告 | 定期`scan_area`で村・遺跡・ポータルを検出したら報告。「あっちに村あるよ」 | 中 | scan_area |
| 変化検知 | 定期`screenshot`+visionで「家が大きくなってる」「畑が増えた」と気づく | 中 | screenshot (実装済) |
| 自己監視 | 低体力/空腹で自衛行動 (逃げる/食べる/休む)。難易度上げたときの生存本能 | 中 | damage evt, eat要use_item |
| 死亡→帰還 | `death`後にリスポーンして「うち」か死亡地点へ戻る | 小 | death evt, waypoint |
| 道具劣化検知 | 手持ちの耐久が尽きそうなら報告・交換提案 | 小 | get_stateのattrs.damage |
| 建築変化の反応 | プレイヤーが近くで建てたものに「すごい」と言う (block変更検知) | 中 | scan差分 |

## 4. 駆動アーキテクチャの選択肢

自律の「心臓」をどこに置くか。併用も可能。

| 方式 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **ローカル自律ループ** | bridgeにattentionループを追加。chat以外のevtでもCodex/Museを起動するようrunner拡張 | イベント即応・現在の構成の延長 | LLM起動コストが頻度に比例 |
| **リモート駆動** | Museのスケジュールタスクがwait_eventをポーリング | メモリ・人格と一体 | 反応がポーリング間隔依存、トンネル必須 |
| **反射層+認知層** | mod内に即時ルール (被弾→逃げる、夜→帰宅等LLM不要の反射) を持たせ、高次判断のみLLMへ | 生存確率がLLM不調でも保たれる | ルール設計が必要 |
| **evt重要度フィルタ** | bridgeでevtに重要度を付け、低重要度は集約して定期処理、高重要度のみ即LLM起動 | コスト抑制と即応性の両立 | 重要度設計が要る |
| **キューイング** | LLM実行中に溜まったevtをキューして終了後まとめて処理 | 現行runnerのqueued機構の拡張で済む | 即応性は下がる |

## 5. 制御・安全

| 案 | 内容 |
|---|---|
| 自律レベル | `autonomy.level` (0=指示のみ / 1=提案のみ / 2=自律実行)。チャット「自由にして」「待ってて」で切替できるのが理想 |
| 行動予算 | 自律行動の回数・時間・資源消費の上限。暴走防止 |
| 透明性 | 自律行動は必ず`send_chat`かjournalへ記録。「勝手にやった」が後から追える |
| 全停止の一貫性 | 「止まって」でskill+task+自律ループまで全停 (`cancel_all`に統合) |
| レート制限 | LLM起動の頻度上限。イベント嵐で課金爆発しないように |

## メモ

- 現状すでに使える部品: `player.nearby`/`time`/`weather`/`damage`/`death`/`pickup` evt、`waypoint`、`emote`、`screenshot`、`say`(chat送信)。案の半分近くはこれらの組み合わせで組める
- `use_item`・`container.click`・`gui_read`が揃うと「寝る」「チェスト整理」「クラフト提案」が現実になる
- 反射層をmod側に入れるかbridge側に入れるかは設計論点。mod側はクライアント再起動で消えるが高速、bridge側は永続だが遅い
